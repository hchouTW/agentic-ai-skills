# agile-development Examples

Canonical worked examples in this skill's own domain, one of eight archetypes
each - see `task-authoring`'s
[references/example-authoring.md](../../task-authoring/references/example-authoring.md)
for the archetype-selection guide and how these are generated and validated
(requires `task-authoring` installed alongside this skill).

| Example | Archetype | Scenario | One-line takeaway |
|---|---|---|---|
| [01-bug-fix-scoping-review.md](01-bug-fix-scoping-review.md) | Contrast | Scoping and reviewing a bug fix for a cart total that is wrong when a discount code is applied | A one-off patch that special-cases the reported codes vs. a failing-test-first fix that states and implements the missing stacking contract with exact decimal arithmetic |
| [02-new-feature-slicing-and-acceptance-criteria.md](02-new-feature-slicing-and-acceptance-criteria.md) | Contrast | Scoping a new "let admins export a CSV of active users" feature request | A broad, unreviewable PR bundling a dashboard, job queue, and email notifier on a silently-guessed "active user" definition vs. given/when/then acceptance criteria, an explicit stated assumption, and the smallest vertical slice with deferred follow-ups |
| [03-production-incident-response-postmortem.md](03-production-incident-response-postmortem.md) | Contrast | Responding to and writing the postmortem for a checkout outage caused by a locking database migration | Root-causing during live impact and a blaming, vague postmortem vs. stabilize-first rollback and a blameless, timestamped postmortem with systemic contributing factors and owned action items |
| [04-trajectory-discount-stacking-bug.md](04-trajectory-discount-stacking-bug.md) | Execution Trajectory | Walking the same discount-stacking bug report (a fourth recurrence) from raw ticket to a verified fix | A reset-instead-of-compound bug that silently discarded one of two stacked discounts, walked start-to-finish: triage, canonical-order fix, deleted superseded one-off patches, and passing regression tests |
| [05-trajectory-database-migration-lock.md](05-trajectory-database-migration-lock.md) | Execution Trajectory | A NOT NULL column migration holds a production table lock for minutes, causing timeouts | Traces the lock to single-statement NOT NULL validation under ACCESS EXCLUSIVE, walked through a three-step nullable-add / batched-backfill / validated-constraint fix verified against an 11.2M-row staging replay with zero timeouts |
| [06-trajectory-dependency-update-silent-break.md](06-trajectory-dependency-update-silent-break.md) | Execution Trajectory | A "minor" dependency bump silently changes rounding behavior, caught weeks later by finance reconciliation | Traces a $0.01-per-invoice discrepancy to a rounding-mode default change untested because no fixture used an exact rounding boundary; pins the mode explicitly and adds a version-independent regression test |
| [07-gated-pipeline-payment-provider-rollout-rfc.md](07-gated-pipeline-payment-provider-rollout-rfc.md) | Gated Pipeline | Drafting and shipping an RFC for a feature-flagged progressive rollout of a new checkout payment provider | Three explicit gates - gap formulation, draft aligned to this skill's own design-doc checklist, and a red-team pass that found a false idempotency assumption and added a required fix before the merge gate |
| [08-gated-pipeline-legacy-billing-strangler-fig.md](08-gated-pipeline-legacy-billing-strangler-fig.md) | Gated Pipeline | Replacing a legacy, untested billing module with a new implementation while it stays load-bearing | Three gates - characterization tests and a seam before any change, a strangler-fig rollout with a deliberately-chosen dependency direction, and a red-team pass that catches a false per-request independence assumption and fixes the routing granularity |
| [09-gated-pipeline-public-api-contract-change.md](09-gated-pipeline-public-api-contract-change.md) | Gated Pipeline | Adding a required field to a shared public API contract without breaking existing external integrations | Three gates - a per-partner capability inventory, an ADR choosing a phased optional-field rollout over an immediate breaking change, and a red-team pass that finds one partner's strict response-schema parsing would break even on an "optional" field |
| [10-decision-tree-incident-mitigation-triage.md](10-decision-tree-incident-mitigation-triage.md) | Decision-Tree | Triaging an ambiguous production incident page and choosing the fastest safe mitigation before root-causing | Formalizes this skill's own Incident Response playbook step into a trigger-to-mitigation matrix, selects the deploy-rollback branch for the reported page, and defines fallback triage if the mitigation fails or the trigger was misclassified |
| [11-decision-tree-pr-review-response-triage.md](11-decision-tree-pr-review-response-triage.md) | Decision-Tree | Reviewing a colleague's pull request and deciding how to respond to each category of finding | Formalizes this skill's own severity-distinction review guidance into a finding-to-response matrix, selects "verify the claim directly" for a PR whose description contradicts its own linked CI run, and defines fallback re-triage for a flaky-vs-real failure |
| [12-decision-tree-staging-vs-production-parity-triage.md](12-decision-tree-staging-vs-production-parity-triage.md) | Decision-Tree | A feature works in staging but misbehaves in production, cause unknown | Formalizes a config/flag/scale/infrastructure/data elimination order into a triage matrix, selects the missing-production-secret branch for a silently-failing scheduled email, and fixes both the missing secret and the silent-failure pattern that hid it |
| [13-elicitation-checkout-latency-ambiguous-request.md](13-elicitation-checkout-latency-ambiguous-request.md) | Elicitation | "Can you make the checkout faster?" - no step, baseline, target, or load condition named | Four clarification questions resolve the request to a single step (payment authorization), a numeric OKR target (p95 under 2s), and a specific load condition (peak-only), scoped as a project rather than an incident |
| [14-elicitation-database-migration-ambiguous-request.md](14-elicitation-database-migration-ambiguous-request.md) | Elicitation | "Can you migrate us off the old database?" - no target engine, cutover strategy, or downtime tolerance named | Five questions resolve it to a Postgres cutover via dual-write/backfill, a zero-downtime SLO-backed acceptance criterion, and a 5-month vendor-EOL deadline with 3 weeks of rollback buffer |
| [15-elicitation-add-caching-ambiguous-request.md](15-elicitation-add-caching-ambiguous-request.md) | Elicitation | "Can you add caching to speed things up?" - no read path, staleness tolerance, or invalidation strategy named | Resolves to one dashboard-summary read path with a 5-minute TTL staleness tolerance and a sub-500ms cache-hit criterion, explicitly deferring write-triggered invalidation |
| [16-adversarial-audit-hotfix-pr-description.md](16-adversarial-audit-hotfix-pr-description.md) | Adversarial Audit | A PR description claiming a "small, safe, one-line" session-timeout bump needs no other changes | Two attack vectors - a doubled steady-state cache-capacity miss and an unaddressed security question about the widened session window - closed with a capacity fix tied to the timeout and an explicit security justification |
| [17-adversarial-audit-backward-compatible-design-doc.md](17-adversarial-audit-backward-compatible-design-doc.md) | Adversarial Audit | A design doc claims an additive `discount_code` API field is "fully backward compatible" | Two attack vectors - a strict-schema mobile client and a frontend view-model key collision - closed by gating the field behind a client-capability flag and renaming the field |
| [18-adversarial-audit-acceptance-criteria-completeness.md](18-adversarial-audit-acceptance-criteria-completeness.md) | Adversarial Audit | A story's acceptance criteria for "update email address" are marked "complete and ready for development" | Two attack vectors - missing re-authentication and no generic-failure response for an unauthorized email-change request - closed with criteria that prevent silent account takeover |
| [19-test-first-story-card-generator-invariant.md](19-test-first-story-card-generator-invariant.md) | Test-First | `create_story_card.py` must reject a story card with no real acceptance criteria instead of silently filling in generic defaults | Red run shows the generator accepting boilerplate criteria; Green run rejects it with a clear message, guarding against "complete-looking" but empty cards |
| [20-test-first-risk-register-entry-invariant.md](20-test-first-risk-register-entry-invariant.md) | Test-First | A risk-register row validator must reject an entry missing Likelihood, Impact, or Mitigation | Red run shows a template-placeholder mitigation passing; Green run's validator rejects placeholder tokens at 100% branch coverage, guarding against "checklist theater" |
| [21-test-first-definition-of-done-invariant.md](21-test-first-definition-of-done-invariant.md) | Test-First | A Definition-of-Done checklist validator must fail when any required item is left unchecked | Red run shows a stub validator always returning done; Green run's real checker fails on an unchecked "tests added or updated" item at 100% line coverage |
| [22-postmortem-production-api-outage-bad-deploy.md](22-postmortem-production-api-outage-bad-deploy.md) | Postmortem | A production API outage (500s spike) after a routine checkout-api deploy | Traces a config/code deploy-ordering race through 5 Whys to a missing pipeline precondition, fixes it with a blocking dependency check, and adds a monitoring rule that pages on a skipped precondition rather than waiting for customer impact |
| [23-postmortem-feature-flag-gap-partial-outage.md](23-postmortem-feature-flag-gap-partial-outage.md) | Postmortem | A feature flag guarded the main request handler but not a secondary retry path, causing errors for a subset of users at 5% rollout | 5 Whys trace to a test suite that never exercised the retry path under "flag enabled"; fix adds a monitoring rule that pages on retry-path 5xx rate before the aggregate error rate crosses its own threshold |
| [24-postmortem-migration-lock-production.md](24-postmortem-migration-lock-production.md) | Postmortem | A migration adding a non-null-default column locked a hot orders table during peak traffic, timing out three dependent services | 5 Whys trace to staging's small dataset masking a lock duration that scales with row count; fix adds a deploy-calendar gate blocking large-table full-rewrite migrations outside maintenance windows |
