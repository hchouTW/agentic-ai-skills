## 1. Incident Symptom & Alert Payload

```
[Analysis group Slack, #vh-bb-analysis, 2025-07-14]
"Our skimmed ntuples from last week's production
(/shared/prod/skim_2025B/output_run1.root) now have a completely
different event count than what we validated - 812,004 events instead of
1,204,331. Did someone overwrite our output?"

--- shared storage access log ---
[2025-07-13 22:04:11] WRITE /shared/prod/skim_2025B/output_run1.root
  job_id: prod-job-88213 (submitted by: vh-bb-analysis, tag: "run1")
[2025-07-13 22:41:57] WRITE /shared/prod/skim_2025B/output_run1.root
  job_id: prod-job-88459 (submitted by: diboson-analysis, tag: "run1")
  <- second job's output path collided with the first job's and
     overwrote it; no error raised by either job
```

Both jobs completed successfully with a zero exit code and no warning;
each group's own local job log showed no anomaly, since neither job could
see the other's write.

## 2. Immediate Triage & Blast-Radius Mitigation

Per `references/02-data-pipelines.md`'s guidance to "preserve input
manifests... and prevent duplicate outputs from retries," the production
team's first action was to check whether the underlying raw ntuple inputs
were still intact (they were - only the shared skim output was
overwritten) and immediately quarantine the shared output directory from
further writes while the collision was investigated, preventing a third
job from compounding the problem. The `vh-bb-analysis` group's original
skim was regenerated by resubmitting their production job under a
collision-free path within the same day, and the corrupted file was moved
aside (not deleted) pending confirmation that no downstream result had
already been computed from it.

## 3. 5-Whys Root Cause Deep-Dive

1. **Why did `diboson-analysis`'s job overwrite `vh-bb-analysis`'s
   output?** Because both jobs' output paths were constructed as
   `/shared/prod/skim_2025B/output_{tag}.root`, and both groups
   independently chose the tag `"run1"` for their respective first
   production run of the 2025B campaign - the path is a function of the
   tag alone, not of which group or dataset submitted it.
2. **Why does the output-path scheme allow two different groups to
   produce the same path?** Because the shared production area's
   directory structure was designed under the assumption that each
   physics analysis group would use its own subdirectory, but the
   `skim_2025B` campaign directory was introduced later as a shared,
   campaign-wide location without carrying that per-group namespacing
   convention forward into its own path-construction logic.
3. **Why wasn't this namespace gap caught before two groups' jobs
   actually collided?** Because the shared production submission tooling
   validates that each *individual* job's requested output path doesn't
   collide with a path *that same submitting user* has already used, but
   it checks uniqueness only within one user's submission history, not
   against all other users' recent submissions to the same shared
   directory.
4. **Why does the submission tooling only check uniqueness per
   submitting user instead of campaign-wide?** Because the uniqueness
   check was written when the shared production area was new and
   lightly used by a single group at a time; it was never revisited when
   the area's usage grew to multiple concurrent analysis groups sharing
   the same campaign directory.
5. **Why did neither job's write receive any warning or error despite
   silently destroying existing data?** Because the underlying write
   uses a plain overwrite-on-write filesystem call with no
   pre-existence check, and per
   `references/02-data-pipelines.md`'s "distributed merges must compare
   expected and processed files/counts and prevent duplicate outputs from
   retries" guidance, no equivalent check exists for two genuinely
   different jobs sharing one path - the pipeline's duplicate-output
   protection was designed for the retry case only.

Root cause: the shared production area's output-path uniqueness check is
scoped per submitting user rather than campaign-wide, so two different
analysis groups choosing the same tag for unrelated jobs produced
identical output paths, and the write itself silently overwrites an
existing file with no pre-existence check - a gap that only manifests once
usage grows beyond a single group per shared directory.

## 5. Blameless Postmortem & Preventative Monitoring Rules

No individual is at fault: both groups followed the normal, documented
convention of tagging their first production run of a campaign `"run1"`,
and neither had visibility into what tag the other group had already
chosen - the collision was invisible to both submitters at the time they
each submitted.

**What worked:** because the raw ntuple inputs were untouched and only the
derived skim output was overwritten, recovery only required resubmitting
one group's skim job, not re-running the full production chain from raw
data.

**What didn't work:** the existing "prevent duplicate outputs from
retries" protection gave a false sense that output collisions were
already handled, when in fact it only covered the single-user retry case
and never considered two different users writing to the same shared
directory.

**Preventative monitoring rule:** `production_tools/submit_job.py` blocks
(non-zero exit) submission of any job whose constructed output path
already exists anywhere in the campaign-wide path registry, and a nightly
scan of `/shared/prod/` alerts the production on-call if more than 0% of
files in any campaign directory were modified more than once within a
1440-minute window outside of an explicit, registered reprocessing job.
