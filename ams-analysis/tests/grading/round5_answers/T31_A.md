## Verdict

Three separate physical effects are each being corrected twice. Each error makes the flux artificially small (and likely distorts its rigidity/time dependence). ## 1. `livetime × exposure` double-counts livetime

By this skill's definitions (`efficiency-acceptance-backgrounds.md`): **exposure is already time-integrated acceptance**, `Exposure = Σ_t A_eff(t) · T_live(t) × transmission(t)` — livetime is a *factor inside* exposure, not something alongside it. The same point is made in the count/response model of `inference-and-unfolding.md`: *"T_j exposure time factor including livetime and geomagnetic transmission... If exposure is already a single number E_j = A_j T_j, do not multiply again."*

`Φ = (N-b) / (livetime × exposure × ΔR)` divides by livetime twice, so it understates the flux by an extra factor of `T_live` per bin (potentially a large effect — quality-time livetime is normally well under the calendar interval once trigger dead-time, prescales, and quality/veto cuts are applied).

The checker confirms this is a first-class check, not a stylistic nitpick — `estimator.applies = ["exposure","livetime"]` alone fires:
```
error: exposure.decomposed_and_composite — exposure (acceptance x livetime x
       transmission) is applied together with acceptance or livetime
```

**Fix:** `Φ_i = (N_i - b_i) / (Exposure_i · ΔR_i)`, using exposure as the single time-integrated quantity — or, if you prefer to write the factors out explicitly, `Φ_i = (N_i - b_i) / (A_eff,i · T_live,i · transmission_i · ΔR_i)`. Never both a composite "exposure" and one of its own factors in the same denominator.

## 2. Response already includes efficiency, and you apply a trigger efficiency again

This is the same invariant-3 violation as a response/estimator double count: *"If a response matrix 'includes inefficiency', say so; then A and ε are already inside it and must not be applied again"* (`efficiency-acceptance-backgrounds.md`), and it's an explicit failure mode in `inference-and-unfolding.md`: *"Response inefficiency counted in both R and A."*

Reproducing this in the checker (response declares `includes: ["efficiency"]`, and the same `trigger_efficiency` effect is also applied in the estimator) gives two independent hits:
```
error: correction.double_applied — effect 'trigger_efficiency' is corrected 2
       times (efficiency in response; efficiency in estimator)
error: correction.response_and_estimator — ['efficiency'] applied both inside
       the response and again in the estimator
```

**Fix:** name explicitly which efficiency `response.includes` — reconstruction efficiency conditional on trigger? Selection efficiency? If the *trigger* efficiency specifically is one of them, remove it from the estimator. If your "trigger efficiency" is a genuinely distinct conditional factor that the response does **not** encode (e.g. the response is built only from events that already triggered, so trigger efficiency is legitimately outside it), that's fine — but you have to state and defend that distinction, not assume it; as written ("the response matrix already includes efficiency" with no qualifier, "and I also apply a trigger efficiency") reads as the same effect counted twice.

## 3. TRD gain drift handled by both a run veto and an efficiency correction

This is the textbook case in `reconstruction-and-data-quality.md`'s four-categories-of-correction table: *"A single physical effect (e.g. a drifting TRD gain) must be treated in exactly one category; if a calibration removes it, a residual systematic covers only what remains, and the efficiency correction does not also include it."* It's also listed verbatim as a failure mode there ("A time-dependent effect corrected once as a veto and again as an efficiency") and again in `calibration-mc-systematics.md`'s double-counting checklist item (e): *"is a time-dependent drift counted as both a veto and a systematic?"*

Checker output for the same `trd_gain_drift` effect applied once as `veto` and once as `efficiency`:
```
error: correction.double_applied — effect 'trd_gain_drift' is corrected 2
       times (veto in selection (run veto); efficiency in estimator)
```

**Fix — pick exactly one:**
- (a) Veto removes the bad-drift periods (their exposure/livetime is reduced accordingly). Any drift *remaining* in the periods you keep is a smaller residual, and only that residual belongs in a systematic — not the full-size correction you'd need if you hadn't vetoed anything.
- (b) Don't veto; absorb the drift fully into a time-dependent efficiency/template-shape correction (TRD discriminant templates keyed to time, per the calibration chain's "TRD gas/gain → template shape nuisance" row) with its own validated systematic.

Record which category owns the effect in the systematic ledger's `double_counting_checks` field.
